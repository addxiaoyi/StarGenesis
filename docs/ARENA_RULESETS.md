# Arena Rulesets

`/genesis arena` opens the player's private editor. The bundled schema-1 release remains readable. New arenas start from schema 2, which adds obstacle cells, team spawn cells, objectives, and victory conditions. The editor adjusts dimensions, duration, unit budget, the `ANY`/`ALL` victory combination, controlled-objective threshold and objective-point threshold. Authors can toggle public reading and cloning separately. Each permission change increments the patch version, and collaborators cannot change these permissions. The map inventory edits a 5 × 3 viewport of obstacle, objective, red spawn and blue spawn cells. `/genesis arena reset` starts a new draft from the bundled schema-2 release. `/genesis arena upgrade` is available through the editor control for a saved schema-1 draft and creates schema 2 at the next patch version.

Preview uses the same checks that run again on save, review submission, approval and match start. `/genesis arena publish` saves the candidate in a bounded server review queue. Reviewers with `stargenesis.arena.review` use `/genesis arena review`, `/genesis arena approve <sha256> <signature>` and `/genesis arena reject <sha256> <signature> <reason>`. The server accepts new decisions only from UUIDs with pinned reviewer keys and valid Ed25519 signatures. Approval durably writes its immutable signed decision before publishing the release. If release writing fails, the same reviewer can retry the same hash and signature after a server restart to resume publication; the candidate is not exposed as a release before its decision exists. Rejection retains its reviewer, timestamp, reason, public-key fingerprint and signature. The author or an authorized editor must still pass the latest published ACL checks when submitting and again when a reviewer approves. See `DESIGN_EXCHANGE.md` for key management and the offline signing command.

`/genesis arena releases` lists the published catalog. `/genesis arena play <design-id> <version>` creates a lobby from that exact published schema-2 version when it has public-read permission. Bare `/genesis arena play` uses the player's saved version. `/genesis arena rooms [page]` lists 20 active or completed matches per page, up to the 256-room storage limit. `/genesis arena spectate <room-uuid>` displays a read-only map viewport and match state to a player who is not seated. A player joins one named slot, for example `/genesis arena join <room-uuid> red:1`. Each slot is assigned to one player UUID. The host must take a slot, every unit slot must be filled, and at least one human must represent each team before the host can start with `/genesis arena ready <room-uuid>`.

Each seated player submits exactly one action for their own slot and the current tick with `/genesis arena act <room-uuid> <tick> <action>`. Actions are `wait`, `north`, `east`, `south` and `west`. Identical retries are idempotent; an action cannot be changed after submission. All actions resolve together. Out-of-bounds and obstacle actions are rejected. When destinations collide, all units in the collision wait at their starting cells. Every turn, including the first turn, resolves after 30 seconds when actions are missing, treating those actions as waits. Late actions are rejected. A player can reconnect with the same account UUID and retain the assigned slot. `/genesis arena match <room-uuid>` reports the public room state. A host can remove a player before the match starts, or stop and delete a room, including its completed checkpoint. The room limit includes completed matches, which remain listed by page until the host stops them.

Reviewers and the server console can run `/genesis arena decisions [page]` to list 20 decisions per page in ascending candidate-hash order, or `/genesis arena decision <sha256>` to inspect a complete decision. The same `stargenesis.arena.review` permission guards both commands. Each displayed record is freshly read and checksum-validated; v3 signatures are verified with the recorded key. Listing validates at most 20 decision bodies per request, within the 8,192-file archive limit. A malformed record on the requested page fails the whole response without returning cached or partial results. Legacy unsigned records are explicitly labeled `legacy-unsigned`.

Inspection includes the exact rejection reason, submitter, reviewer, timestamp, author-key provenance, reviewer fingerprint, Base64 public key and signature. Publication is checked separately against the release catalog: `PUBLISHED`, `APPROVED_AWAITING_PUBLICATION`, or `NOT_PUBLISHED`. A durable approval is not by itself proof that publication completed. Queries never retry publication, delete pending candidates or alter trust. A rejection does not revoke an already existing release. The timestamp, submitter, author-key provenance and publication state are server records, outside the review signature's scope.

Decision records are bounded to 2 KiB on both write and read, including bounded stream reads. Rejection reasons remain limited to 240 UTF-16 code units, with no control characters or malformed Unicode. This accommodates full-length Chinese text and valid surrogate pairs without writing records that cannot be reopened. Valid previously written records larger than the former 1 KiB read limit can be read without migration. The offline signer and Java implementation share multilingual payload/signature test vectors. `arena_review_sign.mjs verify` independently checks a statement against an explicitly supplied reviewer fingerprint; see `DESIGN_EXCHANGE.md`.

If an approval exists but its release write did not complete, an authorized operator can run `/genesis arena recover <sha256> <reviewer-uuid> <original-signature>` from the server console or in-game. The reviewer UUID and signature must exactly match an existing signed approval. This command cannot create decisions, recover unsigned legacy approvals or reverse rejections. Recovery verifies the persisted signature with its recorded key, then checks the candidate's submitter and author-key provenance, latest editor ACL, version constraints and exact dependencies before publication. It retains the original decision bytes and removes the pending candidate only after publication succeeds. A failed write leaves the candidate and approval available for retry. Repeating a successful recovery returns the same release. Reviewer trust rotation or revocation affects new decisions; it does not invalidate replay of a verified, already-persisted approval. Unsigned v1/v2 approvals retain their original reviewer's in-game recovery path.

## Validation

Schema 1 remains a separate wire contract with its existing width, height, duration and unit budget fields. The schema-2 definition is `arena_ruleset-v2.schema.json`; the v1 schema, example and content hash are retained. The global design schema version remains 1 because other design kinds have not changed.

Both formats keep width and height within 4..128, duration within 1..72,000 logical steps, and unit budget within 1..64. Schema 2 bounds obstacles to 512, teams to 2..8, spawn cells per team to 1..16, and objectives to 1..16. The sum of spawn slots cannot exceed the unit budget.

The validator models work as `width × height × unitBudget × durationSteps`, with a maximum of 16,777,216 units. Schema-2 preview also checks cell bounds and overlaps, four-direction connectivity between teams and objectives, each team's optimistic victory threshold feasibility, and round limits. This is bounded geometry validation. It does not prove a competitive balance.

The deterministic `arena/1` simulation accepts one simultaneous cardinal move or wait action per unit. Units capture an objective while standing on it. Each controlled objective adds one point per step. Victory conditions combine current controlled objectives and cumulative objective points with `ANY` or `ALL`. A unique qualifying team wins immediately. At the duration limit, points rank first and current controlled objectives break a points tie. Equal final ranks draw. Room schema `arena-room/1` checksums a bounded roster, actions, tick, scores and simulation state hash. Every room mutation is applied to a copy, flushed to a same-directory temporary file, and committed through an atomic move before becoming visible in memory. A room pins the exact immutable release it uses. At startup, a room resumes only if that release, roster and state hash validate. Active room count is capped at 256.

Strict JSON loading rejects unknown fields and executable content. Review submissions and decisions use bounded binary envelopes with checksums and immutable decision files. New decision signatures bind the candidate hash, reviewer UUID, outcome and exact rejection reason; the server records the timestamp separately. v1/v2 unsigned decisions remain readable and can only be retried by their original reviewer for recovery. Pinned keys authenticate possession of an account-bound key, not a real-world identity, and do not provide cross-server synchronization. The arena simulation does not read or change Minecraft blocks, inventory, land claims, or real currencies. Real-client workflow, spectators, balance testing, anti-cheat, regional isolation and multi-server replication remain outstanding.

## Releases, Permissions, and Dependencies

The bundled arena template is seeded at startup into the server's `published-designs/` directory. Release paths use a SHA-256 digest of the design ID as the directory name, followed by the semantic version and document hash. The ID is never used as a filesystem path.

Submission requires the actor to be the design author or an editor listed in the latest server-published version. The latest published ACL is checked when opening or resuming the editor, on review submission and again when a reviewer approves, so a stale player checkpoint or pending queue item cannot preserve a revoked grant. Only the author can grant or revoke editors. `/genesis arena grant <uuid>` and `/genesis arena revoke <uuid>` update the local draft, increment its patch version, validate and save it. The permission change becomes authoritative after that version passes review and is published. Editors can change arena parameters and submit newer versions while the ACL remains unchanged.

Every dependency is resolved by exact ID, version, and hash from an already published release. Its metadata must grant both `publicRead` and `allowClone`. Hashes prove content identity within this local store and do not prove an author's cryptographic identity.

An existing ID/version is immutable. Republishing identical content is idempotent. Different content under the same version fails, and the editor offers a patch-version increment. Files are size-bounded, schema/hash-validated when loaded, written to a same-directory temporary file, flushed, and atomically moved into place. Filesystems without atomic-move support reject publication.

Player editor checkpoints remain in Paper player persistent data and are subject to the server's player-data save cycle. The release catalog and arena room checkpoints are server-owned and validated on read. Arena room checkpoint writes require atomic-move support. These stores provide no cross-server replication or cryptographic player identity.
