# 版本与迁移

## P0 基线

工程版本 `4.0.0-SNAPSHOT`；设计种类的基线 schemaVersion=1，竞技规则集另有 schemaVersion=2；配置 config-version=1；模拟接口 `genesis-sim/1`，竞技执行器 `arena/1`。这是研发构建，不是 P0–P11 正式发布完成声明。

持久设计格式、配置版本、引擎版本和插件发布版本分别升级。加载未知设计或配置版本时明确拒绝，不猜测兼容性。

## 设计 v0 → v1

`DesignCodec.migrateV0(String)` 验证旧文档哈希，显式把 `metadata.revision` 改为 `metadata.version`、schemaVersion 改为1，重新计算内容哈希，并返回前后哈希、迁移后的 JSON 和不可变对象。普通 `load` 不执行迁移。

v0 是本项目带测试的遗留契约样例，不声称曾在生产服发布。迁移前保留原文与哈希，不覆盖唯一副本；若依赖仍固定旧哈希，必须显式更新依赖并重新验证。Schema/示例/拒绝用例在 stargenesis-design 模块内。

## Arena schema 1 → 2

竞技规则集使用自己的版本。schema 1 文档和发布哈希原样保留，`DesignCodec.load` 继续按旧字段读取；严格拒绝 schema-1 文档中的地图/胜利字段。

`DesignCodec.migrateArenaV1(String)` 先验证 v1 文档的原始内容哈希，再显式生成 schema 2。迁移保留设计 ID、作者、ACL、来源、依赖和地图尺寸，补入两个角落出生点、中央目标和 `ANY` 控点胜利条件，将补丁版本加一并重新计算哈希。为了让默认地图能跑完路径且保持新的工作量上限，迁移会在必要时提高回合时长，并把单位预算调到至少 2 且不超过工作量预算。迁移不会覆盖 v1 内容；迁移 API 返回前后哈希和新文档。玩家编辑器的升级控制对当前已授权草稿执行相同迁移。测试固定 v1/v2 Schema、示例、哈希、拒绝未知字段和地图迁移行为。

## 签名审核格式

Arena 审核提交从 `arena-review/1` 升为 `arena-review/2`，在候选记录及审核决定中保存可选的 Ed25519 公钥指纹。v1 记录读为 unsigned 并继续保留作者、提交者、时间、审核人、结论和拒绝原因；后续写入使用 v2。提交 Hash 与竞技 schema 不变。

`.sgdesign` 使用独立格式号 1，二进制包封装签名作者 UUID、Ed25519 X.509 公钥、SHA-256 公钥指纹、规范 UTF-8 设计 JSON 和 64 字节签名。签名域固定为 `StarGenesis/DesignSignature/1`，并绑定作者 UUID、指纹和设计 JSON 的 SHA-256。未知版本、额外尾随数据、无效 UTF-8、超限字段或签名不匹配一律拒绝。验证结果仍须匹配服务器由 OP 按 UUID 固定的公钥；包内公钥不构成信任。

## 配置与账本

P0 不提供在线 reload 命令。调整 config.yml 后通过受控重启应用；越界预算、未知 config-version 或启用真实结算会拒绝插件启动。先备份插件数据目录，再升级。

模拟时钟、账本和事件 outbox 的核心值对象保存在内存中。P1 网格检查点使用有界二进制编码；玩家 PDC 保存回放基线、当前检查点及有界逐步输入。恢复时重放输入并比较完整快照。该数据随 Minecraft 玩家数据保存，未验证进程崩溃时最近一次玩家数据保存时点。MemoryEventOutbox 不持久化。P9 已实现持久 settlement saga 日志与恢复查询，但没有经验证的第三方库存或经济适配器，不能宣称真实资产可在重启后恢复。

P5 生态检查点写出格式 v4，并能读取 v1/v2/v3。v4 保存全部栖息地格的库存及个体位置。v3 迁移先验证 `ecology/3` 哈希，再将原全局库存及个体放入兼容格 0；v2 迁移先验证 `ecology/2` 哈希并保留能量账本数据；v1 迁移先验证 `ecology/1` 哈希，再以存档个体储能建立 v3 能量基线。Paper 成功恢复后写入 v4 PDC 键并移除 v1/v2/v3 键。旧格式没有自定义反应网络，codec 迁移时采用空网络；旧会话恢复时安装零初始库存的标准生态物种目录，保留旧存档的守恒物质总量并允许继续编辑配方。

共享生态组使用 `ecology-groups/<group-uuid>.eco`，记录格式为 `ecology-group/1`，最多 65,792 字节，组记录含 SHA-256 校验及一个完整 v4 生态检查点。服务器最多加载 128 个组，每组最多 8 名 UUID 成员。启动扫描只枚举小写规范 UUID 命名的 `.eco` 文件；其他文件名会被忽略。被枚举文件若损坏、越界、使用未知版本，或文件名中的组 UUID 与记录 UUID 不符，启动恢复失败，不会自动跳过或改写。每次成员或生态状态变更先写临时文件并要求同目录 `ATOMIC_MOVE` 替换成功，再更新内存记录；文件系统不支持原子替换时命令失败，原记录保留。`leave` 更新名册，所有者的 `disband` 删除整个组文件；个人 v4 PDC 迁移不会改变共享组记录。

P7 的审核申请和结论保存在服务器数据目录 `arena-reviews/`。`arena-review/1` 对申请文档与决定记录提供 SHA-256 校验、有限文件和字节预算；拒绝原因、提交者、审核者与时间保存在不可变决定文件。审核版本不再自动发布，候选必须在提交和批准时两次通过当前发布 ACL 和依赖检查。P8 房间保存在 `arena-matches/<uuid>.match`，由 `arena-room/1` 校验记录校验和、发布版本、座位、部分提交动作、tick、分数与模拟状态哈希。房间状态每次变更先在恢复副本操作，并在同目录原子替换成功后发布到内存。服务器重启后从固定的已发布 ID/版本/哈希恢复。解码器拒绝未知版本、越界文件或状态哈希不符的数据，不执行自动格式推断。

## 后续变更流程

P6 增加独立的 `factory-relay/transaction-v1.checkpoint`，上限为工厂检查点的 2 MiB 加 8 KiB 元数据，保存请求身份、提交前状态摘要、提交后完整检查点、响应和整份日志的 SHA-256。工厂、组织和回执原格式继续读取。启动恢复按日志先提交工厂检查点、再提交完成回执、最后移除日志。未知版本、损坏日志或与现有工厂状态冲突时恢复失败。旧版未完成回执若缺少事务日志，保留其记录并要求管理员核查请求，避免在新 tick 再次执行。

先新增 schemaVersion 与迁移测试，再修改写出版本；保留旧输入回归 fixture，拒绝未知字段和未来版本。破坏确定性的引擎更新必须提升 engine version，旧回放交给对应版本验证器或明确报告不支持。公开 API 改签名须说明消费者、线程边界、预算、迁移与合同测试。
