# Transaction Sagas

P9 adds the bounded settlement contract and durable journal used by future verified economy adapters. A plan has a stable UUID, initiator, provider ID and at most 16 ordered reversible transfers. Transfer amounts are positive integers capped at 1,000,000,000,000. Provider operations use stable per-step idempotency keys for both apply and compensation.

The coordinator persists a `PREPARED` checkpoint before it can call an adapter. It advances one external effect at a time, observes its idempotency key before retrying, and stores the next cursor before returning. Rejection compensates earlier effects in reverse order. An adapter result that cannot be confirmed moves the saga to a review state, where reconciliation queries that same key before work can continue. A recovery test also covers compensation succeeding before its cursor checkpoint fails. On restart, the coordinator observes the compensation key and finishes aborting without repeating the external effect.

Paper stores checksummed binary checkpoints under `plugins/StarGenesis/settlement-sagas/`. Each record is limited to 20 KiB and each server journal to 4,096 sagas. The record budget covers the maximum finite plan, including 16 maximum-length UTF-8 identifiers and a review diagnostic. Writes require a same-directory atomic replacement. Load validates the checksum, plan bounds, identity, revision and legal state transition. Startup validates and reports the journal, then leaves unresolved sagas untouched while no verified adapter is installed.

The adapter contract binds each coordinator to one provider and requires idempotent apply and compensation operations plus a reliable status query. `SettlementGateway.observe(key, transfer, operation)` receives the persisted transfer and its apply/compensation direction on every normal and recovery path. A receipt for the same key with different parameters is not evidence that this step completed. A provider that cannot establish whether an effect happened must report `UNKNOWN`, which stops automatic progression. `/genesis settlement list [page]` and `inspect <saga-uuid>` expose persisted state, bounded diagnostics and provider review keys to OPs. They do not repeat adapter operations; authenticated provider reconciliation and retry wiring remain outstanding.

## Nation resource bridge contract

`NationResourceSettlementGateway` supplies a local bridge contract for allowlisted nation stockpile resources, not a registered or production StarCore adapter. Accounts must be complete canonical nation UUIDs. Requests have positive bounded integer amounts, the `OTHER` category and a deterministic description. Compensation swaps the exact source and target while preserving asset and amount under its own stable key.

The provider ID is `sc.nr.v1.<domain-digest>`, where the suffix is the complete SHA-256 of the pinned, persistent authority-domain ID in lowercase unpadded base32. This 61-character ID fits the existing plan and journal format and binds recovery to the same ledger across gateway reconstruction. Changing the domain changes the provider ID, so the coordinator rejects old plans rather than replaying them into another ledger. Existing plans are never automatically rebound. The gateway also rechecks the live domain before and after provider queries and writes; the provider must atomically enforce the request's domain pin with the actual ledger mutation.

`NationResourceProvider.query` explicitly distinguishes `APPLIED`, proven `NOT_APPLIED` and `UNKNOWN`. An absent receipt, a pending request or unavailable storage alone is `UNKNOWN`. `NOT_APPLIED` requires an authoritative, linearizable proof that no effect occurred and no previous attempt can complete later. Transfer and its receipt must commit atomically and bind the durable key to the entire request. Both `APPLIED` and `ALREADY_APPLIED` write responses require a subsequent durable receipt matching key, source, target, resource, amount, status, category, description and authority domain. A missing or conflicting receipt never advances the saga, and direct gateway calls do not write while observation is unknown.

This contract requires upstream owner-thread execution, durable receipt retention and a single authoritative ledger. It does not implement actor/nation authorization, register Bukkit services or provide a third-party dependency. Contract tests with a simulated provider are evidence about this local boundary only; they cannot establish upstream atomicity or production fault tolerance.

The 2026-11-25 contract evidence is `docs/evidence/p9/nation-resource-contract-20261125.json`. Fourteen gateway tests cover exact receipts, unknown results, domain drift and restart identity, malformed UTF-16 identifiers, apply/compensation checkpoint failures and spent-resource compensation review. Java 21 and Java 25 full-worktree `verify` each pass 343 tests, with runtime settings and artifact hashes in `docs/evidence/p11/p9-p11-verification-20261125.json`.

Real currency and inventory transfers remain disabled. A 2026-11-25 read-only review found an uncommitted StarCore worktree API for receipt-backed nation stockpile resource transfers. That candidate is outside the checked-in StarCore API baseline, is not a pinned dependency, and does not move currency or player inventory; it is not a production adapter. A future pinned implementation must independently prove that it satisfies the bridge contract above. Saga callers must authorize the initiator and nation access because the candidate transfer API does not carry an actor. Compensation can fail if the receiver has already spent the resources, so the existing compensation-review state must remain actionable. The candidate's storage also does not establish safe concurrent writes from multiple StarCore instances; a single authority instance would be required until that is addressed.

No production adapter is registered. `integrations.allow-real-settlement: true` fails startup until a verified adapter is available. The saga journal is local to one server data folder and does not coordinate multiple servers. The current capability extension SPI verifies pinned plugins for read-only capability inspection; it is not yet wired as a settlement gateway, and authenticated business entry points and operator recovery wiring remain outstanding.
