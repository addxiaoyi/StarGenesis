# 工厂与 Arena 玩家命令生命周期

`PlayerCommandQueue`把P6工厂和P8比赛的排队命令绑定到当次玩家连接。一次登录创建一个连接对象；同UUID重连产生不同对象。控制器在转交全局调度器或工作线程前捕获连接，邀请同时捕获双方连接，真正执行时再检查双方仍有效。

| 情况 | 处理方式 |
|---|---|
| 普通命令 | 继续由持有存储目录锁的单一工作线程处理，最多128个待执行任务 |
| 断线 | 玩家事件仅更新不可变连接快照，并尝试合并安排一次清理；不等待服务磁盘调用 |
| 命令队列已满 | 清理任务即使不能入队，连接快照仍已更新；现有命令执行前和完成后都会应用最新快照 |
| 工作线程空闲 | 独立清理任务释放临时状态，不需要再等玩家执行命令 |
| 旧连接尚未开始的命令 | 断线、重连或关闭后跳过，不执行持久化副作用；新连接重新发起操作 |
| 已开始的命令 | 可继续完成保存；结束后清理已退出连接的临时状态。保存成功仍按原规则持久恢复 |
| 玩家重连 | 清除旧连接的查看选择和邀请，再处理新连接的恢复/命令；恢复优先选择活跃比赛 |
| 关闭 | 先清空连接快照、停止玩家命令准入，再关闭worker；正在运行的操作仍遵守目录锁与完成确认 |

服务数据继续归工作线程所有。工厂清理查看选择和涉及离线玩家的邀请；Arena清理查看选择和临时邀请。组织、队伍、比赛、待结算动作和已保存的观察者身份不会因这项清理而删除。Arena邀请登记也通过相同队列串行执行，避免退出清理后全局回调再创建旧连接邀请；已有的即时取消仍保留。

当前连接快照和工作线程上次应用的快照各只持有对应时点的在线连接，不累计保存离线UUID或退出事件。排队任务最多128个，另有一个正在运行的任务；合并清理任务占同一队列容量。连接快照大小随实际同时在线玩家数变化，本实现没有另设在线人数上限。工作线程长时间阻塞时，临时状态清理也要等它继续执行；新连接可立即登记，旧命令不会因此获得新连接身份。

`PersistentWorker`的5秒排空、1秒中断等待和未终止目录隔离保持原合同。P6/P8在关闭时会跳过尚未开始的玩家命令，用户应通过重新登录后的dashboard/replay核对最后成功提交的结果。关闭不能回滚已开始的存储调用，也不承诺超时后强制结束Java线程。Arena草稿仍采用自己的同步生命周期；比赛连接失效先于草稿清理，避免草稿存储等待延迟比赛命令失效。

原控制器命令/退出路由的最小适配器先复现三项失败：满队列丢弃清理、重连后旧命令仍执行、关闭后旧命令及晚到临时状态保留。适配器与原控制器源码、失败输出保存在`evidence/p11/player-command-lifecycle/baseline/`；这不是Paper/Folia实服故障记录。

新增16项单元回归：10项队列生命周期、3项工厂真实存储、2项Arena比赛真实存储和1项Arena邀请接线。包含10,000次身份进出不积累历史、双方连接验证、异常任务后的清理、关闭超时仍保持目录锁、工厂写盘失败后邀请取消及重新邀请、已准入成功写入跨重启恢复、观察者历史选择清理和pending/观战持久数据原字节保留。并发用显式latch控制已准入操作，测试暂停点位于真实服务调用之前；不把它描述为实服写盘中断注入。

本批不修改存档schema、模拟语义或回放hash，没有新增Paper/Folia服务器运行、跨region、热重载、生产容量或真人验收。已有实服证据对应其各自记录的源码与工件；本批验证结果见`evidence/p11/player-command-lifecycle/summary.json`。
