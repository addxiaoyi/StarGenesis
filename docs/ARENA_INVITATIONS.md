# Arena 邀请生命周期

`ArenaInvitations`集中管理`arena match invite/accept/leave`的临时邀请。在线玩家和当前队伍检查仍由控制器及`ArenaMatchService`执行，队伍成员仍通过`teams.json`原子保存。

| 情况 | 行为 |
|---|---|
| 新邀请 | 最多64条；任一玩家只能参与一条待处理邀请，不能同时作为邀请方和受邀方 |
| 接受已准入 | 在调用队伍存储前占用原邀请；处理期间保留容量和双方名额，重复接受被拒绝 |
| 写盘成功 | 移除原邀请；已有队伍状态由正常持久化与重启恢复管理 |
| 写盘失败 | 仅在原邀请仍有效时恢复可接受状态，原邀请人、受邀人和team保持不变 |
| 成员状态拒绝 | 移除无效邀请，允许之后重新邀请 |
| 任一方断线或leave成功 | 取消涉及该玩家的待处理邀请，旧操作失败后不能重新放回 |
| 服务关闭 | 停止新邀请及新接受，清空临时邀请；旧操作完成不会重新加入邀请 |
| 取消后另有新邀请 | 用原准入对象的身份识别完成回调，旧操作成功或失败均不删除或替换新邀请 |

断线或关闭不撤销已经进入队伍存储的操作；已准入的成功写入仍可完成并在重启后恢复。队伍持久操作继续由单一`PersistentWorker`执行，目录所有权和关闭确认沿用`WORKER_LIFECYCLE.md`。邀请登记本身不持有锁等待磁盘，断线取消可以在写盘调用阻塞时完成。邀请不写入存档，也不会在重启后恢复。

原控制器的邀请集合逻辑机械提取后，先复现四条单元失败：没有总量上限、同玩家能组成邀请链，以及断线/关闭清理后旧写盘失败再次加入邀请。它是提取逻辑的回归证据，不是新增实服故障。原控制器、提取源码和失败输出保留在`evidence/p8/invitation-lifecycle/baseline/`。

新增11项测试覆盖以上边界、64名额回收、同一邀请并发接受只进入存储一次、旧操作完成不修改新邀请、真实`teams.json.tmp`写盘失败及重试、关闭期间成功提交的重启恢复。并发测试通过`ThreadMXBean`观察实际存储监视器阻塞后再取消或关闭，避免仅凭延时判断竞态。

本批不改变队伍存档schema、公开规则或比赛回放，也没有新增Paper/Folia真人/多人负载证据。原服务的队伍人数、活跃比赛和存储权限约束仍然执行。P6/P8终局清理、长期多人性能和真人验收继续由`DEVELOPMENT_PLAN.md`与`PHASE_STATUS.md`追踪。
